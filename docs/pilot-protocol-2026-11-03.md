## 1. データの規則

優先順位の高い順に守る。これに反する記録は取らない。

1. 相手の氏名・社名・役職・メール・電話・名刺画像を、タリー表にもリポジトリにも書かない。
2. 出会いは `E-01`, `E-02` … の連番だけで識別する。
3. 手元の現場メモ（紙またはローカルのメモアプリ）には、照合のために
   `scan_id` の末尾6桁まで書いてよい。**リポジトリに入れる集計は件数と割合のみ**。
4. 同意が得られなかった出会いは、件数だけ数え、他は何も記録しない。
5. 会話内容を引用するときは、人物が特定できない書き方にする
   （「製造業の現場DXの話」は可、「◯◯社の◯◯さんが」は不可）。
6. 相手から削除を求められたら §4.4 の手順でその場で消し、タリーには「削除依頼 1」だけ残す。

## 2. 対象となる出会い（eligible encounter）

次の4つすべてを満たすものを1件として数える。

1. 初対面である（過去に名刺交換していない）。
2. 実際に相手の名刺を受け取った。
3. 挨拶で終わらず、相手の仕事の話が1往復以上あった。
4. パイロットでの名刺読み取りに相手が口頭で同意した（§4.1）。

**除外する**: 既知の相手、名刺をもらえなかった、同意が得られなかった、
主催者・受付との事務的なやり取り、自分が名刺を渡しただけの接触。

### 有意な出会い（meaningful encounter）

`tasks/plan.md` の「Action capture」の分母に使う語で、同文書では未定義だった。
ここで次のように定義する。

> eligible な出会いのうち、相手の**課題・関心・次の機会**のいずれかが具体的に話されたもの。

その場では判定せず、24時間チェック（§6-5）で判定する。
Next Action を書くべき相手だったかどうかを、後から落ち着いて数えるための区分である。

## 4. 同意の取り方と文言

### 4.1 名刺スキャンの同意（必須）

名刺を受け取り、会話が一区切りしたところで、10秒で言い切る。

> 「いま、初めてお会いした方との会話を助けるアプリを自分で試していまして、
> いただいた名刺をその場で読み取って、話のきっかけを出す使い方をしています。
> お名刺を読み取ってもよろしいですか。
> 読み取った内容は私の端末と私のアカウントだけに保存して、他の方には共有しません。
> もちろん、お断りいただいても全く問題ありません。」

断られた場合は「承知しました、ありがとうございます」で終える。
理由を聞き返さない。タリーには「同意なし 1」だけを記録する。

### 4.2 音声メモの同意（任意機能。使う場合は必須）

> 「差し支えなければ、いまのお話の要点を忘れないように、
> この場で短く録音させていただいてもよいですか。
> 録音は私の端末にだけ残り、30日で消えます。」

- アプリ内の同意確認を押すのは、相手の口頭同意を得た**後**だけ。
- 録音中の画面を相手から隠さない。
- 断られたら録音せず、文字メモだけにする。
- 自動の文字起こしは当日使わない。下書きが出ても、保存前に自分で読み直す。

保持期間30日と「スキャン削除で音声も消える」挙動は ADR-0009 の決定に合わせている。

### 4.3 イベント共有（当日は使わない）

単独リハーサルなので、チーム共有機能は合成アカウント2件での検証（todo 11）だけに使う。
実際の相手のデータを他人と共有しない。

### 4.4 聞かれたときの答えと削除依頼

| 聞かれたこと    | 答え                                                   |
| --------------- | ------------------------------------------------------ |
| 何のアプリ?     | 自分が作っている、初対面の会話を助ける試作品           |
| データはどこに? | 自分のアカウント内だけ。第三者提供なし                 |
| 消してほしい    | その場でアプリの削除から該当スキャンを消す。名刺も返す |
| 売り込み?       | いいえ。今日は売らない。試用の記録を取っているだけ     |

削除依頼を受けたら、その場で削除まで終わらせる。後でやるとは言わない。

## 5. 当日の手動タリー表

印刷または複製して使う。eligible な出会い1件が1行。

### イベント単位のカウンタ（表の上に書く）

- 参加者総数（概数）:
- 名刺交換した総数（eligible 判定前）:
- eligible 件数:
- 同意が得られなかった件数:
- 削除依頼の件数:
- アプリ・回線の障害回数と内容:
- 充電残量（開始 / 終了）:

### 出会いごとの行

| E番号 | 時刻 | 同意 | スキャン | Brief 間に合い | SAY THIS | 不使用理由 | メモ保存 | Next Action | 相手違い・根拠なし | 備考 |
| ----- | ---- | ---- | -------- | -------------- | -------- | ---------- | -------- | ----------- | ------------------ | ---- |
| E-01  |      |      |          |                |          |            |          |             |                    |      |
| E-02  |      |      |          |                |          |            |          |             |                    |      |

記号:

- 同意: `済` / `断` / `聞かず`
- スキャン: `○` / `×`（×は不使用理由コードを添える）
- Brief 間に合い: `○`（会話中に見られた） / `遅`（会話が終わってから届いた） / `見ず`
- SAY THIS: `使` / `未`
- メモ保存 / Next Action: `○` / `×`
- 相手違い・根拠なし: 発生したら `1` と内容の短い記述
- 不使用理由コード: `T` タイミングが作れない / `S` 社交的に無理 /
  `N` 回線・アプリ不調 / `F` 自分が忘れた / `O` その他（一言書く）
- 備考には人物が特定できる情報を書かない。

## 6. 24時間チェック（11/4 まで）

落ち着いた場所で、タリー表とアプリを並べて記入する。

1. eligible 件数 / 名刺交換総数。
2. スキャンできた件数と、できなかった理由の内訳（コード別）。
3. Brief を会話中に見られた件数 / スキャン件数。
4. SAY THIS を実際に使った件数と、会話が変わった具体例を1〜3件
   （人物が特定できない書き方で）。使わなかった場合は理由だけを書き、
   起きなかった成果を書かない。
5. 有意な出会い（§2）の判定と件数。
6. 保存したメモ件数 / 受け入れた Next Action 件数。
7. 24時間以内に手で送ったフォローアップ件数と、対応する E番号。
8. 相手違い・根拠のない記述の発生件数と内容。
9. アプリの数値との照合（§9 の取得元列）。手集計と差があれば、差の理由を書く。
   理由が分からない場合は `unknown` と書く。
10. その場で困ったこと トップ3。

## 9. スコアカード（分子・分母・取得元・担当）

`tasks/plan.md` の指標表に、分母の定義と担当を補ったもの。本リハーサルの正本はこの表。

| 指標             | 分子                         | 分母                            | 取得元                                                                                   | 担当            | 記録先     |
| ---------------- | ---------------------------- | ------------------------------- | ---------------------------------------------------------------------------------------- | --------------- | ---------- |
| スキャン実行率   | スキャンした出会い           | eligible 件数                   | 当日タリー + `scan_upload_success`                                                       | 現場記録        | §5 / §6-2  |
| Brief 間に合い率 | 会話中に見られた Brief       | スキャン件数                    | 当日タリー + `brief_ready` / `brief_viewed`                                              | 現場記録        | §5 / §6-3  |
| 会話採用率       | SAY THIS を使った出会い      | Brief を見た eligible 件数      | 当日タリー + `say_this_used_yes` / `say_this_used_no`                                    | 現場記録 → 照合 | §6-4       |
| メモ記録率       | メモを保存した出会い         | eligible 件数                   | `conversation_note_saved`                                                                | 照合            | §6-6       |
| アクション記録率 | 受け入れた Next Action       | 有意な出会い件数（§2）          | 製品記録 + `next_action_accepted`                                                        | 照合            | §6-5, §6-6 |
| フォロー実行率   | 完了したフォローアップ       | 受け入れたフォローアップ Action | `next_action_completed` / `next_action_accepted` + 7日チェック                           | 照合            | §7-1       |
| 次回面談率       | 合意した次回面談             | eligible 件数                   | 7日チェック（記述のみ）                                                                  | 照合            | §7-2       |
| 信頼ガードレール | 相手違い・根拠なし記述の件数 | Brief を見た件数                | 当日タリー + `identity_flagged_wrong` / `hypothesis_marked_unhelpful` / `card_corrected` | 現場記録 → 照合 | §6-8       |

読み方の規則:

- 件数と割合を必ず併記する（`3/7`）。
- 分母が5件未満の指標は割合を書かない。1イベントでは十分起こりうる。
- 担当の「現場記録」は当日その場で書く人、「照合」は24時間チェックでアプリの数値と
  突き合わせる人。**本リハーサルは単独実施のため、両方とも高橋**。
  役割を分ける場合はこの2つを別人に割り当てる。

## 11. アナリティクスが取れない場合

PostHog が未設定だと event は届かない（`tasks/plan.md` のリスク）。
2026-10-29 時点で `apps/mobile/.env.local` の `EXPO_PUBLIC_POSTHOG_API_KEY` は空で、
**このままでは analytics は1件も届かない**。キーを設定しない場合、§9 の取得元は当日タリーと製品記録だけになる。

- 当日の朝、実機で `brief_viewed` が届くかを確認する。
- 届かない場合は**手動タリーを一次情報**とし、§9 の取得元から analytics を落とす。
- 後から数字を作らない。取れなかった指標は `測定不能` と書く。
