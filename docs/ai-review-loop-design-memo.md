# AIレビューループによる精度改善 — 設計メモ

- 宛先: 高橋代表
- 対象プロダクト: Miraio Lens（名刺交換）
- 作成日: 2026-09-16
- 位置づけ: 提案への技術的な回答。実装チケットではありません。

---

## 1. 結論

ご提案の「専門家のAIを作ってレビューを繰り返させ、利用者のAIも作ってレビューさせ、
改善ループをAIと少しの人で回す」は、Miraio Lens にそのまま適用できます。
土台の半分はすでにリポジトリに実装済みで、足りないのは「採点する人」の部分です。

ただし、このループでは原理的に上がらない精度が2つあります（§4）。そこを混ぜると
「回しているのに現場の体感が変わらない」状態になるので、最初に分けておきます。

---

## 2. すでにあるもの

| 仕組み               | 内容                                                                                   | 状態     |
| -------------------- | -------------------------------------------------------------------------------------- | -------- |
| 8次元ルーブリック    | 根拠性・個別性・会話での使いやすさ・不確実性の扱い・安全性など、1〜5点で採点する評価軸 | 実装済み |
| 構造チェック         | 禁止表現の混入、根拠IDの取り違え、必須項目の欠落を機械的に検査（AI呼び出し不要）       | 実装済み |
| 合成テストケース35件 | Flash Brief・相互価値・名刺抽出のシナリオ網羅                                          | 実装済み |
| 名刺8項目の実測20件  | OCRが読んだ行を、氏名・会社・部署・役職などに正しく割り当てられるかを実モデルで測定    | 実装済み |

**現状のボトルネックは1点だけです。** 8次元の採点は「人が手で付ける」前提で設計されて
いるため、1周あたりの負荷が高く、改善ループの回数が稼げません。ご提案は、まさに
この採点者を専門家AIに置き換えるものです。

---

## 3. 追加で作るもの — 3つの役

### 役1: 利用者ペルソナAI

名刺交換の実務をディープリサーチで網羅し、需要の高い数パターンをペルソナ化します。
ペルソナは「その人のプロフィール・扱う商材・商談ゴール」を持ち、評価用の入力を量産します。

現在の35ケースは人が手で書いたもので、パターンの幅は人の想像力が上限です。ここを
ペルソナAIに任せると、想定外の業種・立場の組み合わせが自動で増えます。

### 役2: 専門家AI（審査役）

生成された Flash Brief や相互価値の提案を、既存の8次元ルーブリックで採点し、
**点数だけでなく「どこがなぜ弱いか」を具体的に指摘**させます。改善の材料になるのは
後者です。

### 役3: 改善ループ

```
ペルソナAIが入力を生成
   ↓
実モデルが Flash Brief / 相互価値を生成
   ↓
専門家AIが8次元で採点 + 欠陥を指摘
   ↓
指示文（プロンプト）と出力仕様を修正
   ↓
全ケース再実行 → 前回との差分レポート
   ↓（繰り返し）
```

コマンド一発で1周が回り、前回から**下がった項目が必ず表示される**形にします。
一部を良くして別を壊す、という改善の典型的な失敗を検知するためです。

なお、このループは評価専用の経路として実装し、お客様が使う本番処理には載せません。
本番の応答速度とコストに影響させないためです。

---

## 4. 効く所と、効かない所

### 効く（ここが本命）

Flash Brief と相互価値提案の**文章品質**です。具体的には、

- 根拠のない推測が混ざっていないか
- 相手と自分の接点が具体的に書けているか
- 実際に会話の口火を切れる内容になっているか
- 断定してはいけない所を断定していないか

これらは今まで人の目でしか測れず、事実上ほとんど測れていませんでした。
**リターンが一番大きいのはここです。**

### 効かない①: 名刺の文字認識（OCR）精度

評価に使っている名刺画像は合成データで、**斜め・影・反射・折れがありません**。
実際の撮影条件を表していないため、AIレビューを何周回しても実機での読み取り精度は
上がりません。

→ 対処は別枠です。架空の会社名で実物の名刺を印刷し、悪条件で撮影した少数セットを
作る必要があります。これは人の作業で、AIでは代替できません。

### 効かない②: 商談が実際に前進したか

「この Flash Brief のおかげで話が進んだ」は、専門家AIには判定できません。これは
すでに入れてある利用イベント計測（Flash Brief の役立ち度評価、「SAY THIS」の採用率、
人物誤りの報告など）で、実利用から取る指標です。

→ AIループは「出力の質」を上げ、イベント計測が「本当に効いたか」を答える。
役割を分けたままにします。

---

## 5. 最大のリスク — 判定AIを検証せずに回すこと

**生成するAIと採点するAIが同系だと、自分の書き癖を高く評価します。**

これを検証せずにループを回すと、スコアは順調に上がるのに、実際の営業には効かない
文章へ最適化されていきます。しかも数字上は改善しているので、気づくのが遅れます。

対策は1つだけです。

> **人が採点したアンカーセットを30〜50件つくり、専門家AIのスコアが人の採点と
> どれだけ一致するかを、毎回のレポートに表示する。**

一致度が低いうちは、プロダクト側を直すより先に専門家AIの採点基準を直します。
ご提案の「少しの人」を投入すべき一番の場所が、ここです。逆に言えば、人がやるべき
仕事はこれと §4 の実物名刺撮影のほぼ2つに絞れます。

---

## 6. 営業ヒアリングとの関係

メッセージの最初にあった「一番使う営業にヒアリングする」と、AIループは**二択ではありません。**

ディープリサーチから作るペルソナは、公開情報に寄ります。実際の営業が何に困って
名刺交換後の一手を外しているかは、公開情報には出てきません。

- ヒアリング → **ペルソナの答え合わせ**（AIが作ったペルソナが現実と合っているかの検証）
- ヒアリング → **アンカーセットの採点者確保**（何が良い出力かを判定できるのは現場の人）

営業3〜5名に1時間ずつで足ります。ヒアリングを削るのではなく、**ヒアリングの用途を
「仕様を聞く」から「AIの正解を作る」に変える**という理解です。

---

## 7. 進め方

| 段階    | 内容                                                               | 主体             |
| ------- | ------------------------------------------------------------------ | ---------------- |
| Phase 0 | 営業ヒアリング + アンカーセット30〜50件の人手採点                  | 人（営業＋開発） |
| Phase 1 | 専門家AIの実装。アンカーとの一致度を計測し、合うまで採点基準を調整 | 開発             |
| Phase 2 | ペルソナAIの実装。ディープリサーチ → ペルソナ定義 → 入力の量産     | 開発             |
| Phase 3 | ループのコマンド化と回帰差分レポート。以後は自動で周回             | 開発             |

Phase 0 を先に置く理由は §5 の通りです。Phase 1 から始めても動くものはできますが、
その専門家AIが信用できるかを誰も答えられない状態になります。

---

## 8. 決めていただきたいこと

1. **ペルソナの初期本数** — 最初は3〜5本を推奨します。多いほど網羅できますが、
   1周あたりの実行コストと時間が本数に比例して増えます。
2. **営業ヒアリングの人選と時間確保** — Phase 0 の前提になります。
3. **評価実行の予算方針** — 評価は本番と別にモデルを呼ぶため、周回数ぶんの費用が
   発生します。ローカルモデルを併用して常用の周回コストを下げる選択肢もあります
   （プロバイダー非依存の構造になっているため、切り替えは可能です）。

---

## 9. 実装状況（2026-09-18 追記）

この方針のうち、人を必要としない部分は実装済みです。

| 段階    | 状態        | 実体                                                                                               |
| ------- | ----------- | -------------------------------------------------------------------------------------------------- |
| Phase 0 | 土台のみ    | 人手採点シートの形式と一致度の計算（`evals/anchors/`, `judge-agreement.ts`）。採点そのものは未着手 |
| Phase 1 | 実装済み    | 専門家AI（`packages/ai/src/brief-judge.ts`）。8次元スコアと欠陥指摘を返す                          |
| Phase 2 | 土台＋種3本 | ペルソナ定義と入力展開（`persona-fixtures.ts`）。ペルソナ内容の調査による差し替えは未着手          |
| Phase 3 | 実装済み    | 1周を回すコマンドと、前回レポートとの差分（`brief-judge.eval.test.ts`）                            |

残っているのは、いずれも人が入らないと進まない部分です。

- 営業ヒアリングと、それに基づくペルソナの差し替え
- アンカーセット30〜50件の人手採点
- 実物名刺の悪条件撮影セット（§4 の効かない①）

評価は `MIRAIO_RUN_BRIEF_JUDGE_EVAL=1` を付けたときだけ走るため、通常の
`pnpm check` では課金されません。専門家AIは `packages/ai/src/index.ts` から
export していないので、本番の処理経路に紛れ込むこともありません。

---

## 補足: この提案が既存設計と衝突しないこと

Miraio Lens は当初からAI接続部分をプロバイダー非依存に作ってあり、評価用の資産も
本番コードとは別ディレクトリに分離してあります。専門家AI・ペルソナAIは、この分離
された評価側に足す形になるため、**本番の処理経路・応答速度・コストには影響しません。**

また、評価データには実在の個人情報・企業情報を入れない方針を既定にしてあるため、
ペルソナAIが生成するデータもその制約下で扱います。
